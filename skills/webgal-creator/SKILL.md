# WebGAL Creator

Use the author's language, names, key events, ending, and dialogue style. Work with a registered WebGAL project and keep the editable story, synchronization map, and staging outside the game and any public repository.

**新文章的第一轮只交付剧本。** 写好、展示 Markdown 并请用户审核，到此结束本轮。即使已绑定素材库、已有选材记录或用户预先说了选角，也要等用户在看过本次剧本后明确回复确认。素材查询与制作记录的交接方法在第 3 步按需读取。

1. **Identify the project.** Use `project_list`, `webgal_status`, and `project_inspect`. Confirm the intended project, readable files, verified Terre mapping, and write-tool availability before planning any game write. Keep working on the Markdown in read-only mode if those prerequisites are missing. Use a dedicated project for tests.
2. **Deliver the Markdown first.** Draft `story.md` with stable scene and fragment IDs. Ask together about choices that affect the story, character depiction, cost, asset rights, or publishing scope. Show the user the actual Markdown for review. Follow [script format](references/script-format.md). Record their creative approval against the SHA‑256 of the reviewed file bytes. Reread and hash before preparing executable candidates or applying. Re-review affected passages when the content changes.
3. **Resolve asset readiness after script approval.** For a shared library, run the sibling Librarian as described in [assets and staging](references/assets-and-staging.md); this also applies when only Creator was invoked. List the approved story's backgrounds, portraits and expressions, music, ambience, and effects. In the first message asking about sources, show each asset's use and mark it required or optional. Let the user choose what to provide and what to select from `res` item by item if both sources are available. Confirm permitted sources before searching, preparing assets, or delegating. An exclusive source such as `res` bounds every material choice. Compare the list with verified, suitable, authorized assets before generating WebGAL candidates. When there are unresolved gaps, explain their impact and present automatic preparation, user-supplied assets, and an explicitly simplified placeholder version in one grouped question. Honor any existing decision within its scope and start authorized automatic preparation when suitable tools are available. Keep the gate open until every planned cue is ready or its disclosed fallback is explicitly authorized. Script approval and write approval serve separate purposes and do not resolve asset gaps.
   Load the optional sibling [webgal-live2d](../webgal-live2d/SKILL.md) when the current staging request or approved casting uses a Live2D model for the cue being created or changed. A model elsewhere in the library or game does not trigger it.
4. **Preflight batches and sample the draft.** After asset readiness, check operation count, byte budgets, source and target compatibility, and dependencies before each `change_plan` call. Use a non-committable draft for each valid batch. In the candidate preview, pick representative scenes or changed cues and stop once the selected effects are verified. Use `scene_validate` to investigate specific scenes or verify saved versions. Text-only revisions can reuse the existing asset decisions when they leave staging and asset requirements intact.
5. **Protect saved edits and write with MCP.** Read [sync and handoff](references/sync-and-handoff.md) before generating a local patch, resuming, or writing. Resume pending verification first. Base local changes on the saved scene and its revision. Use the bundled read-only helper with the existing script map to prepare precise patches. Obtain this batch's explicit Terre save and all-editor-pages-closed handoff before creating the formal plan. Get separate approval of that plan before applying it. Persist the pending record before `change_apply`. Verify the result and end the session. Follow the recovery and lock checks before telling the user to reopen Terre.
6. **Verify playability and presentation quality.** Read back saved targets and run the project scan. By default, spot-check both candidate and saved versions in Chrome. Select representative scenes or changed cues, stop when the selected effects are verified, and keep screenshots as needed. Use the saved URL from `preview_get_url` after all batches. Only when the user explicitly requests full acceptance or a start-to-ending run, play the saved version through once and capture [five or six key screenshots](references/acceptance.md#chrome-playthrough-and-evidence) during that same run. [Review presentation quality](references/assets-and-staging.md#presentation-quality-review) against the approved story and asset plan. In the delivery, report on portraits and expressions, backgrounds, audio, visual style, and unfinished staging. Name the highest-value improvements and identify accepted placeholders. Record human playtest feedback separately. Follow [acceptance](references/acceptance.md) for release checks and evidence.

Terre installation, project creation, complex branching, live two-way sync, engine changes, exporting and publishing are outside this workflow. Game writes use the existing Write Coordinator. If the connected MCP is unavailable, use only an already authorized local connection to the same MCP service, or continue with the Markdown.
