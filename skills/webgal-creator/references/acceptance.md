# First-release acceptance

Use the installed Skill in Codex with Windows, the existing WebGAL MCP 0.3.0 tool contract, an authorized Terre test project and real Chrome. Use a different isolated registered project from the earlier bare-Codex proof of concept. A local test-only MCP registry may target that project when the current client lacks the tools. Record the connection actually used. Keep the source story, approval, revisions, candidates, map and screenshots in a private creation directory. Release evidence should use only redistributable fixtures.

| Case | Steps and required evidence |
|---|---|
| A. Article to Markdown | Provide only an original short article. Verify the generated `story.md` is readable, has stable IDs, dialogue, narration, thoughts and staging. Check its SHA-256, and show there were no executable candidates or game writes before approval. |
| B. Saved preview | Approve the script, resolve asset readiness, preflight the batch, review its draft and formal plan, and follow the real Terre handoff and application approval. Verify actual files against receipt and plan hashes. Follow [Chrome playthrough and evidence](#chrome-playthrough-and-evidence) for candidate and saved spot-checks or a requested full run. Select relevant checks for quotes, thoughts, narrator name clearing, composition, and looping audio. Stop at the specified effects in a spot-check. Compare the saved presentation with the approved asset plan and report gaps. |
| C. Targeted edit after reconnect | Start a fresh Session and reconstruct the workflow from `story.md`, `script-map.json` and saved MCP reads. Approve a small script revision, apply its local edit, and compare the exact target change and SHA-256 of other scenes. Spot-check affected staging in the candidate and the saved preview. |
| D. Saved Terre changes | In the same scene, have the user change one unrelated line in Terre and save. Edit a different unique fragment and verify the hand edit matches byte-for-byte and its old map baseline persists with `pending-terre`. Exercise overlapping edits, repeated/indeterminate targeting, and a version change after planning. Capture rejection or stop and confirm the rejected attempt had no write. Replan only after resolving the cause with the user. |
| E. Degraded assets | Use a fixture missing a required character visual or matching ambience. Disclose the gaps and obtain a choice before creating executable candidates. Record the selected static visuals, narration, or silence, spot-check the affected fallback in the saved preview and verify that the saved project scan has no missing or invented story references. This can be the same fixture used by B if that fallback is deliberately exercised. |
| F. Interrupted map update | In the isolated project, persist the pending plan and apply with user authorization. End the old session before replacing pending with the synchronized mapping. Reconnect using only persisted state, resolve by `planId` and verify actual files. Advance only proven fragments, preserve unrelated baselines, clear pending atomically, and verify MCP evidence shows exactly one apply plus identical disk hashes before/after resumption. Also cover a mismatched target or partial result with a controlled test. Verify that the map remains pending. When the write session closes with a partial or uncertain result, the user sees a keep-closed instruction until recovery inspection verifies the disk and applicable lock warnings are resolved. |

Capture actual tool commands or calls, pre/post hashes, the application and recovery receipts, and screenshots as needed for the selected preview checks. Compare the observed preview URL to the mapped project. Report failures, missing checks and any known nonblocking engine warnings explicitly. Keep human playtest findings separate from agent and browser observations.

## Chrome playthrough and evidence

- **Default spot-check.** Select representative scenes or changed cues and their expected effects before opening Chrome. Use an isolated candidate preview when practical. For the final saved version, use the official URL from `preview_get_url` after all approved batches are verified. In either preview, open the selected scene directly when supported or advance only as far as needed. Stop once the specified effects are verified. If an effect fails, diagnose and recheck that part. Keep screenshots as needed to show a result or anomaly.
- **Explicit full acceptance.** Only when the user asks for full acceptance or explicitly requests a run from the start to the ending, play through the final saved version once. Keep the candidate check targeted. Pick five or six meaningful beats and capture them in the same full run. Examples include the title, a two-character shot, a single portrait, an expression change, the rain-to-clear transition, and the ending. Adapt the shots to the work and add evidence images only for a specific anomaly.

## Asset workflow regressions

Run each scenario in a fresh conversation using the installed Skill. Use original or redistributable fixtures. Supply a short reviewed two-scene story that calls for two backgrounds, portraits for two important characters, an expression change, music, and rain that continues into scene two, then stops. Have the user reply “I approve this script. You can generate the game.” Provide the stated inventory and tool/authorization inputs. Record the actual first response and tool or candidate actions. Treat the first four cases as separate runs.

| Case | Fixture input | Pass condition |
|---|---|---|
| G1. Empty or unsuitable inventory | No usable art or sound, with no asset strategy selected. Repeat with starter assets that do not match. | Lists the needed assets and impact, offers automatic preparation, user-supplied assets, and an explicit placeholder build in one decision. No executable candidate, plan, or game write is produced while waiting. |
| G2. Complete inventory | All planned needs have verified, suitable, licensed matches. | Summarizes the plan and reuses the existing assets. Proceeds to candidate preparation without asking for an unnecessary choice or replacing suitable files. |
| G3. Explicit placeholder build | The user requests plain stand-in backgrounds, no portraits or expression variants, and no music or rain. | Discloses those specific omissions. Proceeds without repeating the question, keeps the write gates, and reports the outstanding presentation limits at delivery. |
| G4. Authorized automatic preparation | The user explicitly authorizes preparing the missing assets. Suitable image generation or search and audio preparation tools are available under the allowed scope. | Starts preparing the missing assets without asking the same question. Proceeds to executable candidates only once coverage and rights checks pass. |
| G5. Automatic preparation cannot complete | After authorization, a tool fails or the only result lacks verified terms. No fallback was approved. | Names the remaining gap and its impact, offers a path forward, and stays out of candidate generation until resolved. |
| G6. Playable with known quality gaps | A saved preview played to the end, but it has approved stand-in art and omissions or unfinished effects. | Delivery distinguishes playability from presentation and names the important missing portraits, placeholders, audio gaps, style issues when assessable, and unfinished staging that matter. Names the best next improvement without waiting for a follow-up. |

Also verify these focused regressions when changing scope, batching, or preview instructions.

| Case | Fixture input | Pass condition |
|---|---|---|
| Source-only scope | The user specifies only `res`, and a required sound is missing there. Web search and a delegated search are available. | Confirms and propagates the local source boundary before discovery. Reports the missing sound and stays within the allowed root until the user changes scope. |
| Batch preflight | A proposal has 33 operations, an oversized figure, and a scene that depends on an earlier model import. | Identifies the count and compatibility issues before MCP planning. Orders dependency batches and keeps the existing controlled approvals and readback. |
| First asset-source question | The user has approved the script and wants to decide what to provide or select from `res`. | The first source question includes the asset list, each item's use, and whether each item is required or optional. The user can choose sources per item in one reply. |
| Default preview | Only the middle scene changed. The user asks to verify its new effect. | Checks the chosen effect in the candidate and saved result, stops once it is verified, and keeps screenshots as needed. |
| Requested full acceptance | The user explicitly asks to play from the start to the ending. | Keeps the candidate check targeted. Runs the saved result through once and captures five or six relevant screenshots in that same run. |

For dry runs, provide only fixture tool results and test the agent's decisions, messages, and planned actions. State which cases were tested this way. For a real tool run, record the actual tool calls, rights evidence and candidate/writing checkpoints. Use an isolated project and retain all story and write confirmations for any real apply.
